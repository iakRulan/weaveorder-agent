# 技术方案：织序 WeaveOrder

## 1. 项目定位

一句话：**把自然语言目标变成可执行、可校验、可追溯的任务 DAG，并在失败和高风险动作上做编排决策。**

不是“再做一个聊天机器人”，而是做一个**任务编排层**：模型负责理解与决策，引擎负责依赖、状态、校验、恢复和审计。这样即使底层模型换掉，编排能力仍然成立。

赛题三项关键能力的对应关系：

| 关键能力 | 具体实现 | 可演示证据 |
|---|---|---|
| 自主规划 | Planner 输出带 `depends_on` 的 DAG；Replanner 在失败/新信息时修改剩余计划 | 计划 JSON、重规划前后 diff |
| 工具调用 | Tool Registry 声明 JSON Schema；执行器做参数校验、超时、重试、结果引用 | Trace 里的 tool_call/tool_result |
| 多步推理 | Blackboard 保存中间结果；按依赖调度；Verifier 做数值/政策/完整性校验 | 校验失败→修复→通过的完整链路 |

## 3. 核心数据结构

### 3.1 Plan / Step

```json
{
  "goal": "安排上海到深圳的客户拜访",
  "assumptions": ["预算 3000 元", "10-28 去，10-30 回"],
  "steps": [
    {
      "id": "s1",
      "goal": "检索差旅政策",
      "tool": "check_policy",
      "args": {"query": "差旅 机票 酒店 标准"},
      "depends_on": [],
      "success": "返回至少 1 条相关政策",
      "risk": 0
    },
    {
      "id": "s2",
      "goal": "搜索航班",
      "tool": "search_flights",
      "args": {"origin": "上海", "destination": "深圳", "date": "2026-10-28"},
      "depends_on": [],
      "success": "返回至少 1 个航班选项",
      "risk": 0
    },
    {
      "id": "s4",
      "goal": "计算总费用",
      "tool": "compute_trip_cost",
      "args": {"flight_price": "$s2.best.price", "hotel_price": "$s3.best.price", "nights": 2},
      "depends_on": ["s2", "s3"],
      "success": "总费用不超过预算",
      "risk": 0
    }
  ]
}
```

设计要点：

- `depends_on` 形成 DAG，调度器做拓扑排序，互不依赖的步骤可并行。
- `args` 支持 `$step_id.path` 引用，避免把长 JSON 反复塞进提示词。
- `success` 是给 Verifier 的验收条件，尽量写成可判定条件；定性条件才交给 LLM judge。
- `risk` 分级：0 只读，1 低风险写入，2 预订/付款/发送，3 不可逆。`risk >= 2` 必须人工确认。
- 确定性计算优先封装成专用工具（如 `compute_trip_cost`），不让模型心算；模型只负责选工具、填参数。

### 3.2 Trace Event

```json
{"ts": "2026-10-17T12:00:00Z", "type": "tool_call", "step_id": "s2",
 "tool": "search_flights", "args": {...}, "attempt": 1}
{"ts": "...", "type": "tool_result", "step_id": "s2", "ok": true,
 "summary": "3 options, cheapest ¥1280", "latency_ms": 42}
{"ts": "...", "type": "verify", "step_id": "s2", "ok": true, "reason": "..."}
{"ts": "...", "type": "replan", "reason": "总费用 3600 > 预算 3000",
 "changes": ["s2.max_price=1200", "s3.max_price=500"]}
```

事件溯源的好处：报告里的每个结论都能反查到具体工具调用和参数，满足“可审计”。

## 4. 关键算法

### 4.1 Planner

输入：用户目标、工具清单、记忆中的偏好、预算/时间约束。

输出：Plan JSON。

实现策略：

1. **LLM 规划**：System prompt 约束“只能用注册工具、必须输出 JSON、最多 8 步、每步给 success 条件”。
2. **Schema 校验**：工具名必须存在；必填参数必须齐全；`depends_on` 必须引用已存在的步骤；不能有环。
3. **失败回退**：解析失败/校验失败时，用规则规划器生成一个保守计划，保证系统仍能运行。
4. **假设显式化**：把用户没说的假设（默认预算、默认日期）写进 `assumptions`，让用户可纠正。

### 4.2 Scheduler

- 拓扑排序 + 就绪队列；同一层内无依赖的步骤可并发（第一版串行，接口预留 `asyncio.gather`）。
- 全局预算：最大步数、最大 token、最大墙钟时间；超限则停止并给出部分结果。
- 失败策略：单步最多重试 1 次；同一工具连续失败 2 次则触发 Replanner，而不是无限重试。

### 4.3 Verifier

三层校验，从便宜到贵：

1. **结构校验**：返回是否为空、必需字段是否存在、类型是否正确。
2. **确定性约束**：预算上限、日期可行性、政策条款、数值一致性（报告里的数字必须等于工具返回值）。
3. **LLM Judge（可选）**：对“报告是否回答了问题”“建议是否可执行”这类定性条件打分；只在结构/约束都通过后调用，控制成本。

校验失败时输出**可执行的修复建议**，例如：

- `search_flights` 返回空 → 放宽 `max_price` 或换邻近日期
- `calculator` 超预算 → 选更便宜的航班/酒店，或减少住宿晚数
- `draft_itinerary` 缺“费用”段 → 补上 `total_cost` 后重跑

### 4.4 Replanner

触发条件：

- 某步连续失败；
- Verifier 发现约束冲突；
- 工具返回的新信息推翻原假设（例如航班售罄、政策更新）。

策略：只重写**未完成子图**，保留已成功步骤的结果；输出 diff（新增/删除/修改的步骤），写入 Trace。这样既省 token，也能在演示里直观看到“计划变了”。

### 4.5 Memory

- **偏好记忆**：常用出发地、舱位偏好、酒店星级、预算上限。
- **情景记忆**：过去任务的成功计划模板，按任务类型检索，作为 Planner 的 few-shot。
- 存储：SQLite（`memory.db`），第一版可先用 JSON 文件。
- 注意：记忆只做辅助，不覆盖用户本次显式约束。

### 4.6 Approval Gate

- `risk >= 2` 的工具调用前暂停，UI 弹出审批卡片：动作、参数、金额、政策依据。
- 审批结果写入 Trace；拒绝则触发 Replanner 寻找替代方案。
- 演示时这是“可控性”的关键证据：不是 agent 说什么就执行什么。

### 4.7 标准协议与开源生态集成（v0.4）

赛题允许“结合任意 harness，以及 MCP、A2A、Agent Skills、多智能体编排、上下文工程、长周期记忆等技术”。选型结论：**织序本身就是 harness（编排层是本作品的技术贡献，不基于 LangGraph/CrewAI 等框架重写），外围按官方协议规范做轻量集成，零新增第三方依赖。**

框架调研（2026-10，PyPI 权威元数据）：

| 框架 | 最新版 | Python 门槛 | 结论 |
|---|---|---|---|
| mcp（官方 SDK） | 2.3.0 | ≥3.10 | 不引入；按 MCP 规范手写 stdio Server（本项目锁定 3.9+ 零重依赖） |
| a2a-sdk | 1.2.2 | ≥3.10 | 不引入；按 A2A 规范（Linux Foundation）手写 JSON-RPC Server |
| mem0ai / langgraph / crewai | 2.2 / 1.2 / 1.15 | ≥3.10 | 不引入；记忆保留自研 MemoryStore，接口预留适配层 |
| agentscope | 2.0.10 | ≥3.11 | 同上 |

选型理由：① 评分强调可复现与低算力，`requirements.txt` 只有 fastapi/uvicorn/httpx/pydantic；② 引擎已通过 12/12 mock + live 评测，重写风险不可接受；③ 手写协议层恰好证明了编排层的抽象能力——同一引擎可以被 MCP 客户端当工具库用、被 A2A 客户端当远程智能体用。

四项集成（全部已实现并冒烟验证）：

1. **MCP Server**（`mcp_server.py`）：stdio JSON-RPC，暴露 9 个类型化工具给任意 MCP harness；支持协议版本协商（2025-06-18 / 2025-03-26 / 2024-11-05）。
2. **A2A Server**（`a2a_server.py`）：AgentCard（`/.well-known/agent-card.json`，含 v1.0 `supportedInterfaces`）、`message/send`、`message/stream`（SSE）、`tasks/get`、`tasks/cancel`，兼容 v1.0 方法别名；默认 mock 模式可公开部署，skills 目录自动进 AgentCard。
3. **Agent Skills**（`core/skills.py` + `skills/`）：按 agentskills.io 开放标准（2025-12 发布）加载 SKILL.md；技能摘要在自主 Agent 模式注入系统提示（上下文工程），并同步进 MCP/A2A 对外能力声明。现有 `travel-orchestration`、`itinerary-audit` 两个技能。
4. **长周期记忆适配**：MemoryStore（偏好画像 + 情景记忆，白名单 + 敏感过滤）保持确定性实现保证评测可复现；接口与 mem0 等外部记忆服务同构，Python 3.10 环境可替换后端（见 `core/memory.py`）。

## 5. 场景设计

### 5.1 主场景：企业差旅编排

用户输入示例：

> 帮我安排 2026-10-28 上海到深圳的客户拜访，10-30 返回，预算 3000 元，偏好早班机，住客户公司附近。

计划：

1. `check_policy("差旅 机票 酒店 标准")`
2. `search_flights(上海, 深圳, 2026-10-28)`
3. `search_hotels(深圳, 2026-10-28, 2026-10-30)`
4. `calculator(flight.price + hotel.price * 2)`
5. `draft_itinerary(...)`

失败注入（演示用）：

- 第一次航班搜索加 `max_price=1000` → 返回空 → Verifier 失败 → Replanner 放宽到 1500 → 成功。
- 酒店选 800/晚 → 总费用超 3000 → 换 500/晚 → 通过。
- 预订前 `risk=2` → 等待人工确认。

### 5.2 第二场景：经营分析报告（v0.4 已实现）

用户输入：

> 分析 2026Q3 销售数据，定位华东 9 月环比下滑的原因，重点关注数码品类

实现（`analysis_agent.py` + `core/analysis.py`，数据集 `data/sales_2026Q3.csv`）：

1. `file_read` 读取 CSV：字段、行数、缺失值统计（缺失值只披露、不插补）
2. `sql_query` 按大区/品类/月度聚合——标准库 `sqlite3` 真执行 SQL，仅允许 SELECT
3. `report_render` 生成 Markdown 报告：指标以引用方式从 SQL 结果取值，不手抄数字
4. Verifier 独立重算：用同一套查找逻辑从 SQL 结果重新解析每个指标，与报告值比对——不一致即拦截，不会发布

评测（`eval/run_eval.py --suite analysis`，6/6 通过）：黄金值由评测脚本直接从 CSV 独立重算（与被测实现零共享代码）；A05/A06 为同一注入的对照——校验开拦截算错的环比（-29.2% vs 重算 -58.4%），校验关错误数字直接发布；数据源不覆盖的大区诚实失败，不编造。

与差旅的关系：**同一套引擎原语**（Tool Registry 的 Schema 校验/风险分级、EventBus/Trace 事件溯源、确定性校验器、plan/trace/report/result 产物布局），只换工具集。差旅场景的审批闸门在只读分析场景自然退化为无风险动作——风险模型是域无关的。

## 6. 评测方案

### 6.1 任务集

双场景 18 条任务（v0.4）：

- 差旅（12 条 + 1 条 Agent live）：标准/超预算降级/不可达城市、缺日期、中文日期、反向路线、1 晚/4 晚、自主 Agent
- 经营分析（6 条，`eval/analysis_tasks.jsonl`）：骤降归因、正向对照、默认路由、不可达大区（诚实失败）、注入拦截、w/o-verifier 消融对照
- 通用任务（跨场景工具报错恢复、多约束冲突）已由两场景的失败类用例覆盖（T09 不可达城市、A04 不可达大区、A05 注入拦截）

每个任务有 gold 约束与 gold 结果要点；分析场景的黄金值由评测脚本独立重算，与被测实现零共享代码。

### 6.2 指标

| 指标 | 定义 |
|---|---|
| Task Success | 所有 gold 约束满足且最终产物完整 |
| Constraint Satisfaction | 预算/日期/政策等硬约束的通过率 |
| Tool Call Accuracy | 工具名、必填参数、参数值的正确率 |
| Recovery Rate | 注入失败后成功恢复的比例 |
| Human Interventions | 平均人工审批/纠错次数 |
| Cost | 平均 token 与工具调用次数 |
| Latency | 端到端耗时 |

### 6.3 基线

- **ReAct**：`--mode agent`，原生 Function Calling 循环，无 DAG、无确定性 Verifier。live 实测：T13（Agent）65.0s / 9 步 vs T01（DAG）50.3s / 7 步（intern-s2），Agent 多 2 次工具调用且无预审批闸门。
- **Fixed workflow**：`--suite ablation` 中的 `serial-exec` 变体（同层并行关闭，退化为固定串行流水线）。
- **Single-shot**：无工具直接回答，仅定性对比（无法产生可校验费用，天然不满足约束）。
- **Ours**：完整引擎（DAG 并行 + 校验 + 重规划）。

复现命令：

```bash
.venv/bin/python eval/run_eval.py --suite ablation --mode mock   # 消融基线（确定性）
.venv/bin/python eval/run_eval.py --suite ablation --mode live --task T01 --task T02
.venv/bin/python eval/run_eval.py --mode live --limit 4          # T13 = ReAct 基线
```

### 6.4 消融（实测结果）

`eval/results-ablation-mock.md`（确定性，可复现）：5 任务 × 4 变体：

| 变体 | 通过 | 关键差异 |
|---|---|---|
| `ours` | 5/5 | 预算无解 → 显式降级 + 审批；注入故障 → 步骤内修复恢复 |
| `w/o-verifier` | 1/5 | 预算无解任务被误报 ok（¥2960 vs 预算 ¥2000/1500）；注入故障直接失败并扩散到下游 |
| `w/o-replanner` | 5/5 | 本组场景在步骤内确定性修复的覆盖范围内（纵深防御：去掉一层，下一层兜住） |
| `serial-exec` | 5/5 | 结果一致；时间收益见 live 计时（并行轮次 `parallel_rounds>0`） |

Live 复测（`eval/results-ablation-live.md`，Intern-S2 真实运行 12 次，3 任务 × 4 变体）：

| 变体 | 通过 | 关键差异 |
|---|---|---|
| `ours` | 3/3 | 注入故障经步骤内修复恢复（¥2960，预算内） |
| `w/o-verifier` | 1/3 | T02 预算无解被误报 ok（总价 ¥2960 > 预算 ¥2000）；注入故障浪费 2 轮重规划后仍失败 |
| `w/o-replanner` | 3/3 | 步骤内修复覆盖本组故障（与 mock 一致） |
| `serial-exec` | 3/3 | 结果一致；live 耗时受 LLM 延迟主导（n=3 噪声大），并行收益以 `parallel_rounds` 结构性指标呈现 |

结论：**校验层是约束满足率的决定性组件——mock 与 live 双重复测中，去掉校验后 5 任务只剩 1 个、3 任务只剩 1 个；省下的校验时间直接换来不可交付的结果。** 三级恢复各层职责清晰：确定性修复兜住可放宽的故障，重规划处理结构性故障（w/o-verifier 注入任务连烧 2 轮重规划仍失败，反证“先校验、再重规划”的顺序价值）。

目标不是刷到多高，而是证明：**编排层的存在，确实提升了约束满足率和恢复率，而不是只增加了复杂度。**

## 7. 技术难度与创新点

1. **可审计编排**：结论 → 工具调用 → 参数 → 返回值全链路可追溯；报告里的数字可校验。
2. **约束驱动修复**：Verifier 不只判对错，还输出可执行修复建议，Replanner 只改未完成子图。
3. **风险分级审批**：把“能不能自动执行”变成一等公民，而不是事后日志。
4. **双场景复用**：差旅（流程编排）与分析（数据编排）共用同一引擎，证明抽象有效。
5. **低成本**：全部推理走 API，不训练/不微调；书生免费额度可覆盖开发与演示。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 赛题手册要求与假设不符 | 第一优先级拿到手册；架构保持“模型/工具可替换” |
| LLM 输出 JSON 不稳定 | Schema 校验 + 规则回退；计划最多 8 步 |
| 真实 API 不稳定/限流 | mock 模式 + 适配器；演示用固定数据 |
| 时间只有 19 天 | 先主场景闭环，再第二场景；评测只做 12 个任务 |
| 视频/文档拖到最后 | 从 D8 开始积累截图和指标，不等到最后补 |
