为什么是差旅编排

差旅天然包含预算、政策、日期、偏好、审批与失败恢复：它既有真实业务约束，又能让“规划—调用—校验—重规划—审批—报告”完整跑通。织序的内核并不绑定差旅：工具注册表、DAG 调度、Verifier 与 Memory 都可以迁移到采购、报销、运维等任务。

DAG 编排模式

Planner 先产出带 depends_on 的步骤；Critic 预审；Executor 按层并行；Verifier 做确定性校验；失败时 Replanner 改写未完成部分。适合需要审计和确定性的业务。

自主 Agent 模式

把 9 个工具的 JSON Schema 直接交给模型，通过原生 Function Calling 自主选择工具；审批闸门、Trace、报告与 DAG 模式共用。适合探索性任务与开放赋能场景。

03七角色协同与上下文工程

角色输入输出设计意图
Intake一句话目标结构化约束 + 问题 + 假设规则先解析硬约束，模型只补软偏好；模型不能覆盖日期/城市/预算
Planner约束、工具、记忆7 步 DAG JSON严格字段名 + 引用格式；一次结构修复；规则兜底
Critic计划、政策阈值accept/revise + issues执行前发现方向写反、缺步骤、引用错误
Executor分层 DAG工具结果 + 并行批次同层并发、引用解析、超时、风险闸门
Verifier行程草案确定性校验 + 语义验收数字一致、政策带编号、冲突显式
Replanner失败原因 + 已完成结果修订计划保留已完成事实，只改未完成部分；最多 2 轮
Narrator / Memory事实、指标、指标历史可交付摘要 / 偏好画像报告可读，经验可复用

上下文工程的关键选择

  • 不把长 JSON 塞进下一轮 prompt：DAG 用 $s2.best.price 引用 Blackboard 中的结果，Planner 只需知道字段形状。
  • 工具描述压缩：只把名称、参数、返回形状给模型；完整 Schema 留在注册表做校验。
  • 失败上下文：Replanner 只拿到失败步骤、原因、已完成摘要与政策阈值，避免被全量结果淹没。
  • 记忆上下文：偏好画像 + 常飞路线 + 最近 3 次行程，控制在几百字内注入 Planner。

模型经常会把往返方向写反。v0.3 增加 normalize_travel_plan：按日期、目标文本与已有城市自动纠正方向，并在 Trace 中记录 plan_normalized，而不是把错误带进执行。

04并行 DAG 执行与三级恢复

调度

  • 对步骤求分层拓扑序：同层步骤互不依赖，使用线程池并发执行；跨层等待依赖完成。
  • 每一步都有 risk：0 只读、1 低风险写入、2 预订/付款/发送、3 不可逆。风险 ≥ 2 必须在审批闸门暂停。
  • 工具调用有超时；只读工具失败自动重试一次；写操作不自动重试，避免重复副作用。
  • 事件序号由 EventBus 统一分配，并发执行下的 Trace 仍然可读、可回放。

三级恢复

① 步骤内修复

航班空结果 → 移除过严的价格/时段过滤；酒店空结果 → 放宽价格/星级/距离；行程缺段 → 用已确认结果重建。

② 预算优化器

在往返航班 × 酒店的组合中，优先选“预算内 + 政策惩罚最小”的方案；若无解，选最接近预算的方案并降级 + 审批。

③ LLM Replanner

步骤内修复无效时，把失败原因、已完成摘要与政策阈值交给模型重写计划；结果必须再次通过静态校验，最多 2 轮。

不会静默失败

预算 2000 元的用例中，最便宜组合仍需 2130 元。织序不会伪造一个“在预算内”的数字，也不会直接报错退出，而是：保留最接近预算的方案 → 标注红眼/远距离/超支 → 状态降级 → 仍然进入人工审批。审批人看到的是完整冲突，而不是一个漂亮但错误的结论。

场景触发恢复动作最终状态
航班空结果注入 max_price=500移除过滤后重新检索ok · 修复 1 次
预算无解总费用 2130 > 预算 2000组合优化 → 降级 + 审批degraded · 4 条冲突
不可达城市成都→西安无数据不编造；尝试重规划后仍无解failed · 保留覆盖城市说明
往返方向写反Planner 把返程写成上海→深圳normalize_travel_plan 自动纠正ok · Trace 记录变更

05工具层、校验与安全边界

工具是智能体与真实世界之间唯一的写入口。参数先校验再执行，风险先分级再审批，结论先引用再输出。

工具风险返回 / 约束
check_policy0带编号的政策条款、阈值、引用；同 section 最多 2 条，避免证据偏科
search_flights0options / cheapest / best / coverage；只返回数据源真实覆盖的城市对
search_hotels0options / cheapest / best / nights；含距离、星级、退改、含早
compute_trip_cost0去程 + 返程 + 酒店×晚数 + 市内交通；返回分项、total、预算差额
draft_itinerary0行程单 markdown + summary + compliance + facts
policy_compliance0确定性合规检查：价格、时段、距离、晚数、预算
request_approval2审批闸门通过后返回 approved；工具本身不执行下单/付款
get/save_travel_preference0 / 1长期记忆读写；白名单 + 敏感信息过滤

参数校验与纠偏

注册表按 JSON Schema 检查必填、类型、枚举、默认值；同时容忍模型常见错误："2" → 2、"经济舱" → economy、多给字段自动忽略、字符串 JSON 自动解析。校验失败会返回明确错误，而不是把脏参数传给业务函数。

06长周期记忆

偏好画像

跨运行保存常驻城市、酒店品牌、酒店预算、航司、座位、到达时间、是否避免红眼等偏好。每条都带 evidence（用户原话或选择行为）、confidence、更新时间与来源（规则/模型/用户）。

历史行程

每次运行记录路线、日期、预算、实际费用、选择、状态与风险摘要。最近 3 条作为上下文注入 Planner，常飞路线用于提示。

安全边界

  • 白名单键；值长度 ≤ 60；拒绝身份证、手机号、邮箱、密钥等模式。
  • 模型抽取置信度 < 0.7 不写入；写入失败不影响主流程。
  • 用户可在 Web 控制台查看、添加、删除、清空记忆。

注入示例

长期偏好：酒店品牌偏好=亚朵；预算习惯=2800；避免红眼=是
常飞路线：上海>深圳×4；北京>深圳×1
最近行程：
- 2026-10-28 上海→深圳 预算¥3000 实际¥2960 结果=ok
- 2026-10-28 上海→广州 预算¥2500 实际¥2480 结果=ok

Planner 因此会优先在同一品牌/价位内选择，而不是每次从零开始。

为什么不用向量库

差旅偏好是结构化且低基数的，结构化文件 + 白名单比向量检索更可解释、更易审计，也避免把敏感文本写进索引。数据量上来后再替换存储层，不影响接口。

10限制、边界与下一步

已知限制

  • 数据源为确定性 Mock，不依赖外部票务/地图 API；接入真实 API 只需替换 catalog 层。
  • Agent 模式目前是单 Agent + 工具循环，尚未拆分为多 Agent 分工。
  • 记忆为单用户文件存储，生产需要用户维度隔离与向量/数据库存储。
  • 审批等待占用线程；高并发场景可改为任务队列 + 数据库状态机。

下一步

  • 接入真实航班/酒店/地图数据，增加库存与价格时效校验。
  • 把 Verifier 扩展为多规则引擎（按城市/职级/项目维度加载政策）。
  • 多 Agent 分工：Planner / Policy / Booking / Report 各自独立记忆与工具集。
  • 把审批与运行状态迁移到持久化队列，支持多人协作与审计导出。

结论

织序 v0.3 的核心不是“让模型更会聊天”，而是把模型放进一个有依赖、有校验、有恢复、有审批、有记忆的编排系统里。它用确定性守住业务底线，用多智能体提升自适应能力，用 EventBus 把每一步变成可观察、可审计的事实。
